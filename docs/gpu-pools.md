# Bot 独立分配视频／图像 GPU

在 `.env` 启用：

```dotenv
MINIMAX_MANAGED_POOLS=1
MINIMAX_SHARED_WORKER=0
```

管理池模式优先于旧的共享单卡模式。首次启动目标为 **视频 0 张、图像 0 张**，仅 Bot 在线；不会自动启动 GPU worker。之后在 Bot 应用的目标卡数保存在 `.runtime/gpu_pools.json`，Bot 重启后继续协调该配置。生成参数仍按用户保存，GPU 分配是整机全局设置，只有白名单用户可以修改。

## 在 Bot 操作

1. `/gpu` 打开面板。
2. 分别选择视频、图像的 0～8 张卡。
3. 点击“应用分配”。选择数字只修改面板草稿，不会立即更改服务。
4. 点击“刷新”查看可接任务的卡数、物理 GPU 编号、启动中和退出中状态。

旧面板不会覆盖其他用户刚刚应用的配置；设置已变化时需要先刷新。`/service_start` 也打开分配面板。`/service_stop` 将当前图像／视频类别设为 0，另一类的目标不变。`/service_restart` 仅在当前类别的已有任务完成后重启该类别。Bot 始终保持在线。

0 张表示不再接收该类的新任务，已经提交到 worker 的运行中和排队任务全部完成后释放 GPU。等待用户选择数量但尚未提交的任务不占 GPU；提交时如果该类别没有可用 worker，会明确提示使用 `/gpu` 分配。

## 分配规则

- 每个 worker 只使用一张物理 GPU，每张卡只属于视频池或图像池之一。多张卡用于并行处理多个任务。
- 保留现有视频卡，先分配空闲卡满足视频目标，再分配图像卡。卡不足时可接任务的卡数小于目标，目标本身不会被改写。
- 视频仍缺卡时，先回收空闲的图像卡；需要回收忙碌图像卡时停止向它派新任务，等已接收的任务完成后再交给视频。
- 只缩减、扩容或重启其中一类时，保留另一类可继续使用的 worker 和进程。视频优先导致必须回收图像卡时，也会先排空，不会直接中断它的任务。
- 不终止其他应用的 GPU 进程；候选空闲卡同时检查显存、利用率和可见的计算进程。资源不足时后台约每 5 秒重新协调，等待新卡可用。
- 查询队列失败时按忙碌处理，避免误杀任务。启动失败会记录错误并退避重试；日志在 `logs/minimax-h3-pool-{video|image}-gpuN.log`。

例如只有 2 张可用卡，目标“视频 2、图像 2”会先给视频 2 张、图像 0 张；如果图像已有任务，会显示退出中并等任务完成。目标“视频 0、图像 0”会在已有任务完成后释放全部本项目管理的卡。

## 运行环境与 CLI

两类池都使用 [图像运行环境](image-model.md) 中的 `MINIMAX_IMAGE_COMFY_DIR` 和 `MINIMAX_IMAGE_PYTHON`。视频池仅放行原 `COMFY_DIR` 中的 `ComfyUI-MiniMax-H3-Turbo` 节点并读取已有 LoRA，图像池使用原生图像节点。两者复用模型文件、输入和输出目录，各进程显存独立，不需要重新下载已有权重。使用 SDPA、low-VRAM 和 `MINIMAX_IMAGE_RESERVE_VRAM`；旧视频服务的 SageAttention 开关不应用于这个环境。

视频端口为 `MINIMAX_BASE_PORT + GPU编号`，默认 8190 起；图像端口为 `MINIMAX_IMAGE_PORT + GPU编号`，默认 8290 起。两组端口范围必须互不重叠，且不得被其他服务占用。

首次迁移时，先在旧配置下停止原 GPU workers（完成已有任务后），保留或重新启动 Bot；不要同时运行旧 worker 和新管理池。

```bash
bin/minimax-h3-service start             # 只启动 Bot，默认不分卡
bin/minimax-h3-service pools-status
bin/minimax-h3-service pools-set 2 1     # 视频 2、图像 1
bin/minimax-h3-service pools-set 0 0     # 两类排空后关闭
bin/minimax-h3-service workers-start 2   # 只改视频目标
bin/minimax-h3-image-service start 1     # 只改图像目标
```

需要 Bot 在线才能持续协调、等待排空及资源恢复；一次 CLI 调用只执行一次协调。`start` 不带卡数不会修改已有目标；`restart` 重启 Bot 并保留池内 worker，避免连带中断服务。

## 验证

离线测试覆盖 0/0 默认值、视频优先、缩扩容、忙碌排空、重启隔离、无 GPU 时不回退到另一类池、启动后异常的所有权恢复，以及 Bot 面板的草稿、应用、权限和过期配置。

两张空闲卡可运行隔离的真实生成验证：

```bash
python -m tools.smoke_worker_pools --image /absolute/path/to/reference.png
```

工具使用独立状态和测试端口，临时启动视频／图像各一张卡；并行提交视频和原生图像编辑，生成过程中将图像目标设为 0，检查视频 PID 保持不变、图像先完成再释放。随后验证关闭视频不影响图像，最后恢复测试分配为 0/0。它不会修改 Bot 的目标配置；失败时输出独立状态文件位置，便于检查尚未退出的测试 worker。

2026-11-11 实测：视频在 GPU 1、图像在 GPU 2 并行执行；5.167 秒、576×576 的单图 Turbo 视频用时 74.38 秒，原生 4096×4096 内部画布的编辑用时 51.42 秒，交付尺寸为输入的 2048×2048。视频音视频流完整解码成功。图像排空、拒绝新任务、视频 PID 保持、关闭视频后图像 PID 保持等六项检查全部通过，最终测试池为 0/0。记录位于 `.runtime/pools-live-smoke.json`；这些时间包含本例首次加载，不代表通用性能或画质保证。
